# ADR-004: 初期実装フェーズの優先順位

## メタデータ

| 項目 | 内容 |
|---|---|
| 対象ドメイン | プロジェクト全体／開発計画 |
| 変更種別 | 計画・優先順位決定 |
| 可逆性 | 可逆（順序の変更は常に可能） |
| 影響範囲 | 全体 |
| 領域分類 | 非センシティブ |
| エスカレーション | 不要（優先順位の決定はAIが提案し、人間が承認） |
| AIの当初判断 | WSL確認 → CI → DBマイグレーション → 認証 の順を推奨 |
| 人間の最終判断 | 追認（明示的な同意は得られていないが否定もされていない。次の行動で確認） |
| 状態 | 有効 |
| 自律実行カウンタ | 0 |

## 背景

フルスタック実装が完了した時点で、以下の未対応項目が残った。

1. WSLでの動作確認
2. GitHub Actions CI
3. DBマイグレーション管理（golang-migrate 等）
4. 認証・認可
5. OpenAPI単一真実源の徹底（フロント型の自動生成）
6. Chromatic連携
7. 本番インフラ（Terraform + ECS）

## 決定

以下の順序で進める。

```
1. WSL動作確認         → 全ての前提となる。ここで問題が出れば先に進めない
2. GitHub Actions CI   → 自律ループの土台（§2.1）。CIなしでセンシティブ領域に触らない
3. DBマイグレーション  → スキーマ変更を安全に行うための基盤（§2.2 可逆性）
4. 認証・認可          → センシティブ領域（§5.1）。CI完備後に人間レビューで進める
```

## 根拠

- 認証はセンシティブ領域のため、CI で検証ループが閉じる前に触らない
- DBマイグレーションは認証より先。スキーマ変更（ユーザーテーブル追加等）が認証実装に先行するため
- OpenAPI型生成・Chromatic・Terraform は認証の後フェーズ
